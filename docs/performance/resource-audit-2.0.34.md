# 2.0.34 资源与生命周期检查

日期：2026-09-20。基线：GitHub v2.0.28；当前本地构建：2.0.34。未发布。

## 范围
检查应用 54 个生产源码文件（App、Core、Services）的资源创建、持有、失效与释放路径，包括窗口、SwiftUI 托管、显示链接、计时器、观察者、搜索任务、子进程、封面处理和磁盘缓存。对 LyricsKit 接入及 QQ XML 处理做专项检查，运行其完整测试；未把依赖库所有实现或系统框架声称为已完成全面安全审计。

## 确认的问题与修复

| 问题 | 证据 | 处理 |
| --- | --- | --- |
| 屏幕通知中断窗口尺寸 | 原生窗口回归在切歌展开 90 ms 后发布屏幕参数通知，窗口停在中间高度；旧 restoreOnScreen 取消动画却不重新测量 | 相同屏幕目标保留动画；实际屏幕变化按当前歌词和锚点重新定向，完整目标包括位置与尺寸 |
| 播放器微小时间误差导致动画跳变 | PlaybackTimeline 每次快照直接更换锚点，40 ms 回报误差也直接跳变显示进度 | 仅显示时钟将不超过 120 ms 的校正用 300 ms 平滑包络消化；实际播放时间、换句索引、暂停和显式跳转不变，无额外定时器 |
| EDR 通知的线程隔离错误 | Release 并行回归的崩溃堆栈进入 HDRDisplayMonitor.refresh；通知可从后台线程发布 | Objective-C 通知入口改为非隔离，随后弱引用切回主执行器；停止后忽略迟到回调，覆盖检测器和窗口内检测视图 |
| 悬浮窗动画可见性判断不一致 | 显示链接忽略透明悬浮窗的短暂遮挡通知，但外层 WindowVisibilityReader 仍将其判为不可见 | 两层共用同一浮动窗口规则；真正隐藏和关闭仍停止刷新 |
| 已稳定窗口反复启动尺寸动画 | 原生窗口将小数高度取整，而缓存比较仍使用未取整的文字高度 | 先统一原生尺寸，并与屏幕约束后的目标比较；回归检查同一句内多次进度更新不增加缩放代次 |
| QQ 搜索空结果恢复失效 | Release 回归中并行结果的两个整数标签均为 0，完成顺序改变后提示与完整检索身份交换 | 改为两个有明确身份的 async let 结果，保留并行，覆盖提示先到与后到两种顺序 |
| QQ 长歌词解析 CPU 高峰 | 实机一次采样看到约 124% CPU；5 秒线程采样集中在 XMLUtils.removeIllegalContent 的 String.count / 从头按偏移索引 | 改成沿 String.Index 向前遍历，实际删除非法片段才重新扫描，保留原有修复语义 |
| 每秒遍历全部应用 | 线程采样与 readSnapshot 路径一致 | 发现结果按启动、退出通知失效；唤醒重启桥接时更新，终止状态额外检查，保留浏览器排除 |
| 悬浮窗停止后模型、视图未释放 | 修复前 8 轮弱引用测试全部保留模型、控制器和托管视图 | stop 清空托管根、窗口内容和子窗口关系、观察者及回调；模型解除控制器所有权 |
| 计时器强持有自身 | 丢弃 ticker 后弱引用非空且继续触发 | Timer 弱捕获，析构时失效；行为和计时频率不变 |
| 主窗口回调隐式捕获整个 View | showMainWindow 闭包访问 View 的 openWindow 属性 | 仅捕获 OpenWindowAction，避免反向持有模型 |
| 资料库关闭后整库文档仍留在模型 | library 只在再次加载时替换 | 关闭即清空、取消扫描；代次检查阻止迟到结果重新填充；逐文件响应取消 |
| 生命周期边界 | 停止后的唤醒、发现及窗口通知可能仍在主队列中 | 检查停止状态；播放器析构停止循环，Session 析构取消搜索而保留已发起的顺序保存 |
| 长期数据积累 | 歌词路径缓存没有上限；stderr 整文件读入后才截断 | 路径上限 512，淘汰后可从磁盘重新发现；stderr 最多读取 4096 字节 |
| 异常偏移可溢出 | Int.max + 增量、-Int.min | 安全加法并限制偏移范围，重置直接写零 |
| 独立配置目录不一致 | Preferences 注入独立 UserDefaults 后目录仍读标准域 | 缓存目录读取和保存统一使用当前配置域；标准安装行为不变 |

## 不增加实时渲染开销的改动
封面主题使用 32×32 CPU 采样，最多保留最近一张封面；主背景在已有最长边 384 像素的缓存图上烘焙颜色增强。字体测量、布局、转换和边缘遮罩缓存均有数量或内存上限。保持现有逐字、辉光、模糊和弹性动效，不统一降帧。

## 测量与边界
同一份约 19 KB 的多语言 XML，Debug 回归中旧实现约 874–900 ms，新实现约 0.55–1.01 ms，输出一致。这是该处理函数的测量，不代表整个应用或电池耗电降低同等比例。

初始实际播放快照（各约 8 秒）应用 CPU 约 9.45% / 9.52%，RSS 约 203 / 221 MB；歌曲及系统负载并非严格固定，只用于发现持续活动，不作为版本性能差异结论。线程 CPU 的 100% 表示占用一个核心。

系统 IOAccelerator 的 GPU 数值包含 WindowServer 和其他应用，不能直接归因 LyricsX，也不能换算瓦数。短时 CPU 快照、RSS 或通过构建均不证明“绝无泄漏”。释放测试验证具体对象与任务的生命期，长期真机播放仍需观察。

## 长音字符强调检查

对照 AMLL 的字符错落强调和 Better Lyrics 的字体／辉光分层说明，保留独立原生实现：真实高亮进度不变，只让长音的字符变换依次启动；五次平滑包络在端点速度与加速度归零。组合字符及连字沿用原生字形簇，连接文字保留整词变换。每个原生文本 run 共用一个辉光层，短音、已结束的词和减少动态效果模式不拆分绘制。

## 原生窗口帧率比较

修复可见性门控后，Release 测试宿主验证原生显示链接持续活动、请求帧率正确、歌词时钟真实前进。相同双语逐字场景在 120 Hz 屏幕上按隐藏、120、60、60、120、隐藏的顺序各采样 6 秒，另有预热和阶段稳定时间；没有同时构建或操作其他界面。

| 状态 | 测试进程 CPU 均值 | 整机 GPU 指标均值 |
| --- | ---: | ---: |
| 隐藏 | 4.68% | 35.08% |
| 120 帧 | 26.18% | 46.42% |
| 60 帧 | 15.59% | 46.18% |

60 帧在该场景减少约 40.4% 的测试进程 CPU，仍保留所有动效，但采样频率变低。隐藏阶段包含测试宿主循环开销，不能当作正式应用的空闲占用。GPU 读数包含其他应用与系统合成，两个可见阶段没有可归因的显著差异，不能承诺 GPU 降幅或电池节省比例。保留现有帧率选项，不强制修改用户选择。

原始数据：`/tmp/lyricsx-gpu-234-corrected/{cpu.json,gpu-system.json,test.log}`（临时诊断文件，不随应用发布）。旧的未建立活动显示链接的样本已排除。

## 切歌阻塞与文字跳格复查（本地构建 249）

用户确认设置页后，继续针对主界面播放与双窗口切歌检查。封面路径原来在 MainActor 内同步执行 ImageIO 缩略图生成；现在由串行 `ArtworkDecoder` 在后台完成解码及像素解压，主线程仅发布结果。仅缓存最近一张（压缩数据小于 8 MB、缩略图最长边 640 像素）；过期任务、同一歌曲更新后的旧封面、停止后的回写均被取消检查拦截。

字形缩放／位移的各个绘制分支统一使用 `disablesSubpixelQuantization`，避免运动中微小位置被量化成跳格。静止和高亮分支也使用同一策略，避免激活瞬间切换策略。该选项对应 Apple 的文字动画说明：
https://developer.apple.com/documentation/swiftui/text/layout/drawingoptions/disablessubpixelquantization

原生双窗口 Release 测试使用独立模型、100 行原创双语逐字文本、2400×2400 PNG、相同播放及六次切歌顺序，不连接真实播放器。修复测试宿主的窗口曝光与事件循环后才接纳数据，要求窗口真实曝光且显示链接正在送帧；未曝光的早期样本全部排除。

| 播放阶段测试进程 CPU | 62.16% | 39.13% |
